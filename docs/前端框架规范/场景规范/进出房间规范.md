# 进出房间规范

本文统一规定从大厅或亲友圈进入房间，以及离开房间后的返回流程。具体玩法只负责房间内操作，不得各自实现进出房间。

## 1. 公共要求

- 进入前记录来源：大厅、亲友圈或大联盟；从亲友圈进入时同时记录对应亲友圈。
- 创建、加入和返回房间一次只能执行一个；请求期间按钮置灰，禁止重复提交。
- 进入过程中保留当前界面并显示统一加载层；房间首帧完成后才移除来源界面。
- 任何阶段失败都停留在来源界面，恢复按钮并显示失败原因。
- 已有活动房间时，禁止再次创建或加入其他房间，只提供“返回房间”。
- 进入和退出不得出现黑屏、闪屏、旧界面闪回、重复房间界面或无关弹窗。

## 2. 从大厅进入房间

### 2.1 创建房间

1. 点击大厅“创建房间”。
2. 选择玩法和规则；点击“创建房间”。
3. 创建期间按钮显示“正在创建”并禁止再次点击。
4. 创建成功后取得房间信息，加载对应资源并进入房间。
5. 进入成功后关闭创建界面；进入失败则保留创建界面供重试。

### 2.2 加入房间

1. 点击大厅“加入房间”。
2. 打开数字键盘，输入六位房间号。
3. 六位房间号完整后点击“确定”；提交期间“确定”按钮置灰。
4. 加入成功后关闭数字键盘并进入房间。
5. 房间不存在、已结束、人数已满、条件不符或玩家已有其他活动房间时，留在大厅并显示明确原因。

### 2.3 返回活动房间

客户端本地保存的房间号、房间对象、来源页和断线前状态只能作为恢复线索，不能作为“仍在房间”的依据。登录完成、应用恢复、WebSocket 重连和点击“返回房间”时，必须先调用服务端权威恢复查询；只有服务端同时确认房间实例仍有效、房间处于可恢复阶段、玩家仍有有效席位且路由版本匹配时，才显示或执行“返回房间”。点击后不得再次执行创建或加入。

服务端返回“无活动房间、房间已终结、房间已解散、玩家已离席/被移出、旧房间实例、旧路由或版本不兼容”时，客户端必须执行第 8 节的原子清理并返回来源页，不得继续加载该房间资源、自动申请解散、轮询旧房间或再次进入旧桌。一次小结算不等于房间终结；是否可恢复只服从服务端权威房间生命周期和剩余局数。

## 3. 从亲友圈进入房间

### 3.1 房间列表进入

1. 进入指定亲友圈，展示该亲友圈的房间列表。
2. 点击房间条目直接申请加入；点击“详情”只打开房间详情，不立即进入。
3. 在详情中点击“进入房间”后才申请加入。
4. 加入成功后记录当前亲友圈为返回位置，再进入房间。

### 3.2 快速加入

1. 点击“快速加入”，展示当前亲友圈允许的玩法。
2. 只有一个已选玩法时可直接使用该玩法；存在多个玩法时由玩家选择。
3. 需要密码时先完成密码验证，再申请加入。
4. 系统按亲友圈规则选择可加入房间；没有合适房间时按亲友圈配置决定是否创建新房。
5. 成功后进入房间；失败则返回快速加入界面并显示原因。

### 3.3 在亲友圈创建房间

1. 从当前亲友圈打开“创建房间”。
2. 选择该亲友圈允许的玩法和规则。
3. 创建的房间必须归属当前亲友圈，不能创建成大厅个人房间。
4. 创建成功后记录亲友圈来源并进入房间；失败时保留创建界面。

### 3.4 当前房间

亲友圈检测到玩家已有房间时，显示当前房间信息：玩法、房间号、局数、人数和在座玩家。

- 未开局：显示“进入房间”和“退出房间”。
- 已开局：只允许“进入房间”；不能在亲友圈外部直接退出，提示玩家进入房间处理。

## 4. 进入房间的统一顺序

无论来自大厅还是亲友圈，顺序固定为：

1. 校验房间号、玩法、亲友圈身份、密码和加入条件。
2. 服务端确认创建或加入成功。
3. 取得本房间的玩法、规则、资源和连接信息。
4. 显示统一加载层并加载房间所需资源。
5. 打开房间场景并建立连接。
6. 收到完整房间状态，完成房间基础界面首帧。
7. 移除加载层和来源界面，允许玩家操作。

前一步未成功，不得提前关闭来源界面或展示可操作的空房间。

## 5. 退出房间

### 5.1 未开局

- 是否允许退出只以服务端 `cardsDealt` 字段为边界，与玩家是否准备及其他发牌前选择无关；`cardsDealt=false`（未发牌）时任何在座玩家（包括房主）点击左上角返回按钮都可退出房间。
- 房主退出后由服务端转移房主身份；房间已无其他玩家时关闭空房。房主需要主动关闭仍有玩家的房间时使用“解散房间”。
- 退出或解散失败时留在房间，不得先返回再补请求。

### 5.2 已开局

- 进行中的房间不能使用普通“退出房间”直接离开。
- 需要结束房间时，在房间内发起解散流程；未解散时继续留在当前对局。
- 从亲友圈的“当前房间”查看到已开局房间时，只能进入房间，不能在亲友圈界面强制退出。

### 5.3 已结束

房间正常结束后显示结算。玩家点击“返回”时结束房间运行界面，再按进入来源返回。

## 6. 返回位置

| 进入来源 | 退出或结束后的返回位置 |
|---|---|
| 大厅创建、房号加入、活动房间恢复 | 大厅主界面 |
| 亲友圈房间列表、快速加入、亲友圈创建 | 原亲友圈主界面 |
| 大联盟房间 | 原大联盟或其所属亲友圈界面 |

返回亲友圈时恢复原亲友圈、原房间列表和必要的筛选状态，不得只返回大厅后让玩家重新进入亲友圈。

## 7. 返回时的界面清理

1. 服务端确认玩家已离开、房间已解散或房间已结束。
2. 关闭房间内弹窗、结算层、操作层和房间连接。
3. 清理房间资源与临时状态。
4. 打开目标大厅或亲友圈，并等待其首帧完成。
5. 最后移除过渡层；同一时间只能有一个可交互主界面。

## 8. 旧房间会话残留与重连循环防护

### 8.1 唯一恢复入口

- 创建、加入、登录恢复、前后台恢复和断线恢复必须汇入同一个房间会话协调器；同一玩家同时只允许一个恢复任务，重复触发复用当前任务或明确拒绝，禁止多个页面分别恢复。
- 恢复查询必须携带客户端所知的 `roomId`、`roomInstanceId`、`membershipVersion`、`routeVersion`、`stateVersion` 和连接代次；缺少旧值时允许查询“我的权威活动房间”，但客户端不得指定其无权恢复的席位。
- 服务端必须返回明确且稳定的恢复结果，至少区分：允许恢复、无活动房间、房间已终结、房间已解散、席位已失效、房间实例过期、路由过期、版本不兼容和可重试的临时不可用。禁止用空对象、通用失败或连接关闭让客户端自行猜测。
- 只有“允许恢复”才能取得短期连接票据、加载玩法 Bundle、打开房间界面并拉取权威快照。客户端不能先进入旧桌再补做校验，也不能凭本地内存、缓存房间号或旧 WebSocket 推送恢复牌局。

### 8.2 原子失效与有限重试

- 收到任何不可恢复结果时，必须以同一房间生命周期代次原子完成：取消未完成请求、退订旧推送、关闭旧连接、使迟到回调失效、清除房间 Store/持久化恢复线索/待提交操作/计时器/选牌和动画状态、释放房间资源，并只导航一次到大厅或原亲友圈。
- 已终结、已解散、已离席或旧实例属于确定性结果，禁止自动重试，禁止继续发起解散、离开、准备或牌局操作。服务端已确认终态时，客户端不以“补发解散”作为清理手段。
- 只有服务端明确标记为可重试的网络或临时服务错误才允许指数退避并加入抖动；重试必须有次数和总时长上限。同一组旧房间实例、席位版本和路由版本再次被拒绝时立即熔断，向玩家提供“重试查询”和“返回大厅”，不得自动反复进房、重复加载资源或无限刷新。
- 所有响应和推送在回写前必须校验页面/房间生命周期代次、`roomInstanceId`、`membershipVersion`、`routeVersion` 和 `stateVersion`；旧连接、旧房间和迟到消息一律丢弃，不能重新打开已经关闭的房间。

### 8.3 验收门禁

至少覆盖以下真实流程并记录请求次数、资源加载次数、恢复结果、房间实例与版本变化、控制台和服务端日志：活动牌局断网后只恢复一次；非最终小结算后可正常续局；最终结算、解散、离席、被移出后带旧缓存重启不会回旧桌；游戏节点故障接管后只连接新路由；同账号多端接管后旧连接失效；迟到响应和推送不会重开房间；网络反复抖动达到上限后停止自动恢复。任一流程出现重复进房、重复加载、连续解散、无限重连或必须重启服务器/人工改数据才能解除，均判定不通过。

### 8.4 多人掉线与暂停恢复表现

- 客户端只上报连接和操作意图，不以本地在线人数、倒计时或历史结算数据决定继续、托管、结算或销毁。收到恢复快照后必须展示服务端返回的权威生命周期、当前阶段、当前操作者、在线/托管状态、暂停原因和截止时间。
- 收到 `SUSPENDED` 状态时保留房间界面但禁止牌局操作，明确显示“等待恢复”及可执行动作；截止时间到达后客户端只能重新查询权威状态，不能本地宣布结算、解散或反复重连。服务端恢复为 `PLAYING`、进入结算或终态时，客户端按新的 `stateVersion` 单次切换。
- 历史小结算、回放或房间快照加载成功不等于恢复完成；只有恢复结果同时指明下一动作及有效权威截止时间，客户端才进入可继续状态。缺少下一动作或截止时间必须报告协议异常并停留在可恢复失败界面，禁止显示一个看似正常但永远不能操作的牌桌。
- 验收必须覆盖多人连续掉线、全员掉线、当前操作者掉线、暂停期间重连、恢复后再次掉线和服务端节点接管。每种情况都必须在限定时间内看到继续、规则结算/退款或解散之一，且客户端不会假死、无限加载、重复提交或要求玩家重启应用。

### 8.5 重连积分展示与退款

- 所有玩法重连后必须以服务端权威账本一次性恢复局前积分、当前可用积分、当前局冻结/底池积分和已结算变化；客户端不得沿用断线前缓存继续累加，也不得因筹码动画、历史结算或迟到 Msg 重复扣分。
- 牌局未形成权威结算便异常终止或判为无效时，客户端等待服务端逐笔原路退款结果后再展示最终积分。金花等已经丢入底池但未进入合法结算的积分必须全部退回原玩家；客户端不得自行计算或生成补分。
- 积分快照、结算和退款版本不一致时，房间进入“积分核对中”的不可操作状态，保留明确提示和 `traceId`，直到服务端返回一致快照；禁止先关闭房间并用本地数字掩盖差异。
- 验收必须记录断线前后服务端账本版本、扣减流水、冻结金额、结算或退款流水和客户端显示值，证明积分守恒、结算与退款互斥且各自至多一次。
