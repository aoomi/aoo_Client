# 前端架构规范

本文只规定技术选型、目录、分层和依赖边界。

## 工具与基线

- 引擎：Cocos Creator `3.8.8`。
- 语言：TypeScript。
- 场景与资源必须由 Creator 资源数据库管理，保留 `.meta` 和 UUID。
- 客户端提交操作意图并展示结果；牌局状态、合法性和结算由服务端裁决。

## 固定目录

```text
assets/
├── Common/       全项目公共能力
├── Login/        登录
├── Lobby/        大厅
├── Club/         亲友圈
└── Games/
    ├── CommonRoom/
    ├── Mahjong/
    ├── Poker/
    ├── LongCard/
    └── WordCard/
```

业务内部按需使用 `Prefab/Atlas/Audio/Spine/Font/Code/Config`，不创建空目录。地区只保存身份、配置和真实差异，公共玩法实现只保留一份。

- 麻将、长牌、字牌的大类配置统一位于 `Client/assets/Games/<大类>/Packs/Config`；扑克公共配置唯一位置为 `Client/assets/Games/Poker/Common/Config`。配置不得放入 `Pack01` 或任一具体玩法包；只有存在真实配置资产时才创建 `Config` 及其 `.meta`，禁止用空目录或占位配置伪造完整性。
- 大类 `Config` 只保存共享或注册配置；玩法私有代码、Prefab、Atlas、Audio 等保留在对应玩法目录。配置迁移必须移动而非复制，并保留原 `.meta` 与 UUID；迁移完成后不得留下旧目录或重复副本，用户已删除的 `Poker/Packs` 和旧 `Pack01` 不得恢复。

- 模块专用图片与图集统一归入 `Client/assets/Modules/<模块>/Atlas`；跨模块共享视觉只保留在 `Client/assets/Common/Atlas` 的单一权威位置并由各模块引用。不得为了模块“自包含”复制共享资源，也不得同时保留 Common 原件和模块副本。

- 大厅预制体唯一正式目录为`Client/assets/Lobby/Prefab`，不得继续引用旧目录`Client/assets/Lobby/EnabledPrefab`。
- 大厅目录迁移保留原资源身份：`Lobby/Prefab.meta` UUID为`f9ac9375-37f5-48fa-a44e-31b10148d750`，`Lobby_Main.prefab` UUID为`098ca929-38eb-41fb-b1fc-64c7f224e8a5`；路径迁移不得通过重建资源改变UUID。

## 分层

- `Common`：网络、资源、导航、弹窗、加载、存储、音频、日志、权限、多语言和适配。
- `Games/CommonRoom`：所有牌局共有的房间表现与生命周期。
- 牌类 `Common`：麻将、扑克、长牌、字牌各自共有的牌面与操作能力。
- `Packs`：玩法差异资源；编号是稳定资源组，不是版本号。
- 具体玩法：只包含自身规则适配、配置和独有表现。

依赖只能从具体玩法指向牌类公共层，再指向全局公共层，禁止反向依赖。

每个发布模块、每个 `game_code` 玩法和每项现行功能都必须纳入依赖审计，同时检查 TypeScript import/调用、Scene/Prefab/UUID、嵌套资源、动态加载路径、Bundle、字符串事件、全局单例、本地存储和网络 Msg，不得仅依赖 import 图宣称解耦。具体玩法之间禁止直接引用代码、Prefab、内部配置和可变状态；真实共性只能上移到正确的玩法族、牌类或全局公共层，差异通过配置或策略注入。

所有“可解耦且净收益明确”的依赖都必须整改，但禁止为解耦而创建一对一空接口、Manager/Helper/Facade 转发链、全局事件总线或重复状态。验收时必须证明全部调用方已切换、旧直接依赖已删除、无反向/循环/隐藏依赖，并通过构建、Creator 重导入与真实 E2E。

## Bundle 与加载

- Bundle 名称表达稳定模块，不携带版本、地区或 CDN 信息。
- 一个资源只有一个权威归属，禁止复制进多个 Bundle 或 `resources`。
- Bundle 必须按“启动最小集 → 全局公共 → 大厅/亲友圈业务 → 牌局公共 → 牌类公共 → 玩法族 → 地区真实差异”分层；资源归属以真实消费者和变化边界为准，不得把专属资源塞入 Common，也不得为了目录独立复制公共资源。父子 Bundle、Prefab 嵌套、脚本 import、UUID、动态路径和图集依赖不得形成循环或让进入 A 业务被迫下载 B 业务专属资源。
- `Client/assets/Common/Prefab` 的唯一 Bundle 为 `common`，当前只包含六个根层公共 Prefab：`CommonHead`、`MsgDrift`、`Message`、`Numpad`、`SettingsPanel`、`WaitNet`；用户已在 Creator 删除的公共 `NoticeBar` 不得恢复。公共 `UINoticeBar` 注册、NativeMaps 当前公共路径、大厅加载与注册、`LegacyNoticeBarController` 均不再属于现行链路；玩法专属历史 NoticeBar 映射、社交消息和红点功能不受影响。
- `Client/assets/Games/Common` 的唯一父级 Bundle 为 `games-common`；其 `Scenes`、`Prefab` 等子目录不再声明嵌套 Bundle。全局公共 `common-prefab` 与牌局公共 `games-common` 必须按职责分开，不得以名称相近互相兜底。
- `Client/assets/Games/Poker/Common` 的唯一父级 Bundle 为 `poker-common`；公共小结算与大结算目录继承该 Bundle，不得另建 `poker-small-settle`、`poker-big-settle` 嵌套 Bundle。涉及目录 `.meta` 时必须通过 Creator 3.8.8 正常取消子 Bundle、重导入并执行 Preview/E2E，禁止直接伪造 Library 缓存。
- 长牌与字牌大类继续使用稳定 Bundle 名 `games-longcard`、`games-wordcard`；目录 `.meta` 必须显式启用 `isBundle:true`，不得因归档资源而改名或另建别名。
- 主包只保留启动、版本检查、最低登录 UI、下载器和错误恢复。
- 进入页面或房间时只加载所需 Bundle；次要语音、动画和皮肤后台加载，不阻塞主流程。
- 下载进度必须来自真实、已校验的资源清单，禁止假进度。

### 图片与图集分类

- 图片必须按业务层级和用途归入唯一目录：独立大背景、可复用 UI 小图、牌面/棋子、头像与远程图、动画序列帧、Spine/粒子专属贴图、动态生成图和地区专属图片不得混放。文件所在目录、Bundle、图集和 Scene/Prefab 使用方必须表达同一归属。
- 只有生命周期、加载时机、采样参数、压缩格式和使用场景相近的多张小图才允许合入同一图集。大背景、极少使用的大图、跨业务图片、远程更新图片、不同压缩/过滤/Wrap/颜色空间要求的图片以及不能同时释放的资源不得强行合图。
- 图集不得跨越 Login、Lobby、Club、Modules、Games 大类或不同玩法专属边界；真正公共的小图可位于最近公共层的一份公共图集。禁止因一张共享图片让玩家下载整个无关业务图集，也禁止同一图片在多个图集或散图中重复保存。
- 图集必须检查尺寸上限、实际占用率、透明空白、Padding/Extrude、旋转、Trim、MipMap、纹理压缩、像素格式、平台最大纹理限制和 DrawCall 收益。超大低占用图集、频繁更新造成整包失效、拆得过碎导致请求过多或混入不同生命周期资源都必须调整；不能只用“DrawCall 更少”证明图集合理。
- SpriteFrame、Atlas、Spine、粒子和序列帧必须保留 `.meta`/UUID 引用闭包。移动或重组图集必须通过 Creator 3.8.8 正常导入并验证所有 Prefab、动画轨道、动态加载路径和构建产物，禁止重建 UUID 或直接修改 Library。

### 玩家进入体验

- 登录、大厅、亲友圈和每个玩法房间都必须定义“可交互首帧”的最小关键资源集。进入关键路径固定为：取得权威目录/房间许可 → 并行获取必要数据与可并行资源 → 校验关键 Bundle → 打开界面 → 应用完整权威状态 → 首帧可交互；非关键动画、音效、皮肤、表情、回放和二级弹窗延后加载。
- 预加载必须基于高概率下一步和网络/内存条件：登录成功后可预取大厅最小集，大厅确定玩法或已存在活动房间后才预取对应牌类/玩法 Bundle。禁止启动时预加载全部游戏，也禁止无房间许可先下载旧房间资源；预取任务必须可取消、去重、限并发并服从前台关键请求优先级。
- Bundle 清单使用内容哈希、版本、大小和依赖图；CDN 支持压缩、缓存、断点续传、并发范围和失败回源。相同内容只下载和解压一次，缓存命中必须复用；更新时只失效变化 Bundle，不得因无关图片变更让公共包或全部玩法重新下载。
- 必须测量冷启动、热启动、首次进入、缓存后二次进入、弱网、丢包、资源更新和断线重连场景的 DNS/TLS、目录、下载、校验、解压、反序列化、Scene/Prefab 创建、状态同步及首帧各阶段耗时、字节数、请求数、峰值内存和主线程长任务。禁止只统计加载动画显示时间或用假进度替代真实指标。
- 优化目标是在正确性、资源完整性和可恢复性不降低的前提下，最小化点击到可交互首帧的等待时间。不得通过提前关闭加载层展示空界面、缺图界面或不可操作牌桌，也不得通过永久持有所有 Bundle 换取二次进入速度；必须同时报告冷/热进入收益、内存代价和释放结果。

## 启动与场景过渡

- Web 启动遮罩由 `PresentationTransitionCoordinator` 在运行时统一创建并自注入必要样式；不得依赖 Preview 不会加载的 Web 构建模板 CSS。
- 启动遮罩即使挂在 `body` 下，也必须使用覆盖视口的 `fixed` 定位并脱离普通文档流；显示或隐藏都不得扩展页面高度、产生纵向滚动或在登录 UI 下方残留启动/失败界面。
- 启动 Logo 只允许存在于场景外启动遮罩这一层；遮罩与 Logo 各保持单实例，资源路径由协调器中的单一映射提供，`web-mobile`、`web-desktop` 模板不得重复硬编码图片路径。
- `SceneRouter` 解析场景业务挂载容器时必须按 `cc.Canvas` 组件识别，不得把节点名 `Canvas` 作为结构契约；节点改名不能导致 `MainScene` 已启动但大厅无法挂载。
- 场景启动完成以 `Director.EVENT_AFTER_SCENE_LAUNCH` 为权威信号；`loadScene` callback 只保留错误处理和兼容通道，不得因成功 callback 偶发缺失让导航永久停在加载态。收到目标场景启动信号并完成大厅挂载后，方可进入 `LOBBY_PRESENTED` 并隐藏启动遮罩。
- 目标场景完成首帧交接后必须隐藏遮罩并同步不可见语义；普通大厅表单和返回大厅仍使用唯一公共 `WaitForm`，不得借启动遮罩建立第二套常规加载界面。
- Preview 验收至少覆盖桌面 `1280×720` 与移动端视口：同一时刻仅有 `1` 个 Canvas、`1` 个启动遮罩和 `1` 个启动 Logo；登录场景就绪后遮罩隐藏，`body` 不得产生纵向溢出。

## 新功能接入

1. 优先组合现有公共组件和资源包。
2. 只有真实差异才新增玩法文件或资源。
3. 配置发布后冻结版本、资源清单和协议能力。
4. 页面、场景和资源改动按场景规范完成 Creator 同步。

禁止恢复全局脚本大目录、按省市复制整套玩法、业务自建网络/导航/加载框架，或用 Creator 2.x 文件冒充 3.8.8 原生资源。

## 禁止补丁堆叠

- 功能开发和问题修复必须先定位唯一根因、权威状态源、完整调用链和生命周期边界。禁止在既有错误流程外围持续增加特殊 `if/else`、页面级兜底、重复重试、延时调用、布尔补丁状态、旧名称轮询、兼容转发或复制实现来绕过根因。
- “补丁”不按提交次数、代码行数、文件名或注释判断。出现同一业务在多个 Controller/Manager/Prefab 分别修正、同一状态有多个布尔值或缓存表示、正常流程依赖异常兜底才能成功、新修复需要识别旧修复、分支顺序决定结果、临时开关无移除条件等证据时，必须按补丁堆叠处理。
- 确认补丁堆叠后，不得继续追加补丁。应以服务端权威契约、客户端单一状态机、统一入口和清晰所有者重构该业务流程，删除被新模型替代的旁路和重复状态；公共能力只保留一份，真实业务差异使用配置或策略表达。
- 业务主流程一旦确认依赖补丁链，重写属于强制整改，不得降级为可选优化。涉及正确性、积分、结算、房间活性、安全或核心进入流程时，在新主流程完成、全部调用方切换且旧补丁不可达前禁止发布。
- 重构不是无边界重写。开始前必须建立现有行为、协议、数据、Scene/Prefab 绑定、动态加载和异常恢复基线，列出必须保留的外部兼容；按可回滚阶段迁移全部调用方，新旧双栈只能位于集中适配入口并设置截止版本和删除条件，禁止长期双写或双状态源。
- 重构完成必须验证正常、边界、并发、断线、取消、迟到响应、资源释放和回滚路径，证明新流程独立成立且旧补丁已不可达。只把旧代码移动到 Helper、增加 Facade、换类名、套一层接口或保留原分支并新增统一入口，不算完成重构。
- 废弃功能、旧补丁或过渡方案只有在代码定义、运行实例、import/调用、Scene/Prefab/Animation 序列化绑定、UUID/meta、动态路径、Bundle/资源注册、配置、测试和构建发布入口全部清退后才算删除完成。用于过渡验证的临时 Scene/Prefab、脚本、资源、mock、快照、配置和测试数据必须在验证后删除；有长期价值的测试必须收敛为正式回归测试。清理后必须通过 Creator 重导入与关闭重开、编译/构建、引用扫描和真实 E2E 证明零残留。
- 开发过程的旧登录/大厅/亲友圈/玩法入口、旧启动 Scene、隐藏按钮/手势/调试面板、测试跳转/快捷进房、旧深链接、旧资源加载键、旧域名/端口/Msg、旧构建脚本和平台模板入口必须逐项登记。无明确所有者、用途、鉴权、环境隔离、现行回归测试和删除日期的非主入口属于开发遗留，必须清退。
- 前端干净验收必须达到：每项能力只有一个现行入口；无旧 Scene/Prefab/Bundle/节点绑定、无孤儿 UUID/meta/注册、无备用旧链、无临时开关/调试入口/测试凭证、无注释掉的旧代码、无重复实现和无期限兼容；例外必须位于集中边界并有流量、截止版本/日期和负责人。

## Bug 与死循环防治

- 所有前端流程必须对空值、越界、异步竞态、重入、迟到 Msg、页面切换、节点销毁、Bundle 卸载、重复点击、断线重连和服务端版本差异有明确行为，禁止吞错、假成功或销毁后回写。
- 任何循环、递归、Tween/动画回调、Promise 链、事件相互触发、状态观察回写、定时器、轮询、重连、页面跳转和资源重新加载必须具有可证明的收敛条件、最大次数/总时长、取消和熔断及对称释放；禁止忙等和逻辑上无限重入旧页面/旧房间。
- 上线前必须用可控时钟、故障注入、快速重复操作、断网/恢复、迟到/乱序 Msg 和长时间运行验证调用次数、CPU、内存、节点、监听、定时器和资源引用始终有界。无法证明终止性的生产可达路径不得发布。

## 用户设置存储边界

- 所有用户主动设置必须登记生效范围、数据级别、默认值、本地存储 key/路径、服务端字段/API/Msg、权威方、版本/TTL、同步冲突和清理规则；不得由各页面自行拼接 key 或双写。
- 仅影响当前设备的音量、振动、画质、帧率和设备布局等表现偏好可仅存本地；需跨设备、重装恢复、影响服务端业务/权限/安全的设置必须以服务端为权威，本地只能是可失效镜像。客户端不得把 Token、密码/PIN、私钥或实名资料保存到普通 localStorage 或明文文件。
- 登录、退出、切换账号、多设备、离线后上线、清缓存、重装、升级和销号必须通过真实测试，证明不丢设置、不串账号、不用旧本地值覆盖新服务端值，且敏感数据按规则删除。

## 全流程全链路验收

- 所有现行前端流程都必须从真实 Canvas 上的用户操作开始，追踪 Scene/Prefab/组件、状态、Bundle/资源、请求/Msg、服务端裁决与数据副作用、响应/推送、UI 回写、异常恢复、终态和资源释放。直接调 Controller/Handler、mock 响应或仅检查 UI 不得代替真实 E2E。
- 每条流程必须验证正常、边界、无权、重复操作、并发、超时/取消、断网重连、乱序/迟到 Msg、服务重启、版本/配置变更、回滚和退出清理，并固化 buildId、协议/配置版本、地址、roomId/operationId/stateVersion/traceId、截图、控制台、网络和资源释放证据。
- 验收前必须证明旧 UI/节点绑定、Scene/Prefab/Bundle/动态路径、旧请求/Msg、旧域名/端口/路由、旧配置/开关和旧加载入口已删除，构建与运行时无旧链路命中。只隐藏 UI、默认关闭或旧链路“通常不可达”不得通过验收。
- 任一现行流程未测、任一必测分支无证据、任一旧链路仍命中，都必须阻断对应发布。

## 客户端运行内存治理

- Login、Lobby、Club、Modules、Common 和每个 `game_code` 必须分别建立启动、进入、峰值、退出、切换、重连和反复进退后的内存基线，覆盖 JavaScript heap、DOM/WASM/原生内存、纹理显存、音频、Scene/Prefab/节点/组件、Bundle/Asset/Atlas/Spine/粒子、网络缓冲、快照/回放和第三方 SDK。
- 每个对象与资源必须有所有者、生命周期和对称释放。禁止全局 Store/单例长期持有已退出页面或玩法，未解除事件/定时器/Tween/回调，销毁节点仍被闭包引用，资源计数不对称，以及无界数组/Map/队列/历史。退出功能后内存必须在合理 GC/引擎释放窗口内回到可解释的稳定平台。
- 内存优化优先消除泄漏和无用常驻、缩短生命周期、按需加载、去重、取消无用预取、调整不合理纹理/图集和减少每帧分配。不得通过降低必要画质、删功能、缺资源、破坏动画、减少恢复状态、丢失积分/回放/审计证据或增加进房等待换取低内存。
- 优化必须使用同一 buildId、设备、画质、资源和用例做前后 heap snapshot/allocation/GPU 对比，并回归帧率、首帧、画质、动画、操作、重连、结算和真实 E2E。内存未显著下降或任一质量指标退化，不得判定优化成功。
