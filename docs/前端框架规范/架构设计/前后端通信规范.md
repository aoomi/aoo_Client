# 前后端通信规范

本文只规定客户端通信边界。

- HTTP 与 WebSocket 统一通过公共通信层，业务不得自行创建连接。
- 请求必须携带协议版本、会话身份、追踪标识；写操作还需幂等标识。
- 玩家、陪玩和机器人身份只读取服务端返回的权威字段 `user_type`：`0=普通玩家`、`1=陪玩`、`2=机器人`。客户端不得通过 `ppk` 的任意位、显示 ID、`ppk` 长度、昵称或账号号段推断、伪造或改写身份。
- 同一业务域使用统一消息信封，禁止同义消息和历史别名继续产生新写入。
- 服务端状态版本必须单调递增；客户端忽略过期、重复或不属于当前房间的消息。
- 重连先恢复权威快照，再继续接收增量消息，禁止客户端凭旧内存补牌局状态。
- 客户端只发送操作意图；合法操作、牌局推进、分数和权限由服务端决定。
- 每个玩家只收到其有权查看的数据，隐藏信息不得先下发再由前端隐藏。
- 票据不写日志、不长期落盘、不放 URL；鉴权失败或切服失败必须安全退出当前业务。
- 超时、断网、重复点击和迟到响应必须有统一处理，关闭页面后不得由旧响应重新打开界面。

## 房间会话恢复协议

- 客户端缓存的 `roomId` 和房间状态只作查询线索；恢复资格、房间生命周期、玩家席位和当前路由全部由服务端权威裁决。启动、重登、前后台切换和 WebSocket 重连必须先走统一恢复查询，未经允许不得加载房间资源或打开旧桌。
- 恢复请求与所有房间操作必须关联 `roomInstanceId`、`membershipVersion`、`routeVersion`、`stateVersion`、连接代次和 `operationId`（只读查询可不使用操作幂等号）。服务端返回短期连接票据，不向客户端暴露或固化内部游戏节点地址。
- 恢复结果必须是机器可判定的稳定枚举，并明确 `resumable`、`retryable`、清理指令和 `traceId`；至少覆盖允许恢复、无活动房间、房间终结/解散、席位失效、实例/路由过期、版本不兼容及临时不可用。内部消息类型统一使用 `Msg` 简写，禁止新增 `Message` 等平行命名。
- 确定性不可恢复结果必须终止自动恢复并原子清除旧会话；只有明确可重试的临时错误允许有限指数退避。重试达到上限或同一旧版本再次被拒绝时必须熔断，禁止反复进旧桌、重复加载 Bundle、连续申请解散或无限重建连接。
- 客户端以生命周期代次和上述版本字段过滤所有迟到响应与推送；服务端以席位、实例、路由和 fencing token 拒绝旧连接与旧操作。双方都不得将“收到过结算 Msg”简单等同于房间终态，多局房以权威生命周期和剩余局数为准。
- 协议测试必须覆盖正常重连、最终结算后重启、主动离席、被移出、房间解散、节点接管、多端登录、乱序/重复/迟到 Msg 和网络抖动，并断言恢复、资源加载和解散请求均有明确上限。

## 房间活性协议

- 每个非终态房间响应和恢复快照必须包含权威生命周期、玩法阶段、当前操作者、在线/托管席位状态、`lastProgressAt`、下一动作类型、绝对截止时间和 `stateVersion`。只有历史结算或快照而没有下一动作与截止时间，属于不完整恢复，客户端不得据此宣称已恢复。
- 连接状态 Msg、操作超时 Msg、托管 Msg、暂停 Msg、恢复 Msg 和终态 Msg 必须由服务端状态机产生并具备幂等序号。客户端倒计时只展示服务端绝对截止时间，不生成结算、销毁或牌局推进事实。
- 多人掉线后服务端必须依据玩法规则返回继续托管、进入 `SUSPENDED` 或进入终态之一；`SUSPENDED` 必须包含稳定原因码、最大暂停截止时间、允许的客户端动作和 `traceId`。客户端到期只能查询权威状态，禁止本地循环重连代替服务端处置。
- 契约测试必须模拟单人、多人和全员掉线、当前操作者掉线、暂停中重连、调度任务丢失及节点接管，并断言每个非终态状态始终存在下一推进任务或最终处置截止时间，结算/退款和终态 Msg 至多一次。

## 局内积分与重连协议

- 所有游戏的积分、金币和筹码只读取服务端权威账本。客户端提交下注、跟注、加注或其他投入意图，不直接扣改权威积分；界面可先表现等待态，但必须由带 `ledgerEntryId`、`operationId`、账本版本和 `stateVersion` 的服务端结果确认。
- 重连快照必须同时返回局前积分基线、当前可用积分、当前局冻结/底池积分、已结算变化、账本版本和最后流水序号。客户端必须原子替换积分视图并丢弃旧版本 Msg，不把本地缓存、动画中的筹码数量或历史结算覆盖到新快照。
- 未产生合法权威结算而异常终止或判为无效的牌局，服务端必须发送引用原扣减流水的退款结果；金花等已丢入底池但未结算的积分必须逐笔原路退回。客户端只能展示权威退款，不得本地补分，也不得因重连重复播放而重复请求退款。
- 结算与退款必须互斥且至多一次。协议必须明确区分 `PENDING`、`SETTLED`、`REFUNDED`，迟到、重复和乱序的扣分、结算、退款 Msg 按账本版本和流水号丢弃；任何金额或版本不一致都进入不可继续操作的对账中状态并提供 `traceId`。
- 契约与真实测试必须覆盖下注后断线、多端/多人掉线、请求超时、重复 Msg、结算前后节点崩溃、无效局退款和退款后迟到结算，并以服务端流水及守恒结果为准，不能只断言界面数字。
